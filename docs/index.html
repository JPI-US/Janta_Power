01 Four FSMs, three threads

The single largest change against master: src/runtime/main.rs — 848 lines of sequential boot phases followed by one enormous loop {} — is gone.

In its place, src/main.rs is 105 lines of pure wiring. Four cooperative state machines run on three threads, each owning its own context and communicating only through a mailbox and a shared bulletin board.

MachineThreadTickEntry stateOwns
Motiondedicated, 8 KB100 msMotionInitstepper, encoder, relay, limit switch, homing, sun tracking
Networkdedicated, 8 KB10 msWifiInitializeWi-Fi, RTC/SNTP, MQTT, boot validation, OTA, telemetry
Buttonsshared “Auxiliary” group, 8 KB100 msButtonsCheckPressedmaintenance / CW / CCW edge detection
LED100 msLEDCheckRGB status indicator

The two messaging primitives

Mailbox is point-to-point: unbounded crossbeam channels indexed by FSMAddress, carrying FSMCommand. Motion pushes serialized telemetry to Network this way; Buttons pushes press events to Motion.

Bulletin is broadcast: one Mutex<Option<FSMState>> every machine holds an Arc to. FSMState is deliberately tiny — two booleans, maintenance_mode and ota_active. That second flag is the whole mechanism behind §08.

The engine itself is 400 lines in crates/infrastructure/fsm/. Each step calls State::process(ctx, mailbox, bulletin, previous_state) and gets back Running(next), Hold, or Stopped. A Group round-robins machines on one thread and drops any that stop; when the group empties, the thread exits.

02 One env var becomes the fleet identity

Everything that reaches AWS — topic prefix, TLS client certificate, MQTT client ID, Jobs namespace — is derived at compile time from a single line in .env.

The third branch is new on this branch and is the reason the Jobs migration works at all. Mqtt now carries a public thing_name field, because AWS IoT Jobs topics are namespaced by Thing name. This fleet sets Thing name equal to MQTT client ID, so tower_9001 must exist as a registered Thing in us-east-1 with that certificate attached.

Transport is mutual TLS with no username or password: Amazon root CA, device certificate and private key are all baked into the binary as CStr constants. Endpoint, hardcoded in one place:

mqttS://a2exykcl6t998u-ats.iot.us-east-1.amazonaws.com:8883

03 The MQTT layer grew a receive path

crates/infrastructure/network/src/mqtt.rs went from 162 to 294 lines across three commits. Three substantive changes, one of which fixed a silent dead end.

The inbound queue was never fed

On master, message_queue was allocated and try_receive() was public — but the event thread handled Connected, Disconnected, Published and Error, and never Received. Nothing was ever enqueued. The entire remote command channel was dead code that returned None forever.

Two queues, split by topic prefix

Both consumers run on the same Network thread, so a single queue would let the command handler swallow a job response mid-OTA. Ingestion now routes on prefix:

// mqtt.rs — inside the connection event thread
let target = if topic.starts_with("$aws/") {
    &job_message_queue     // drained by wait_for_job_message(timeout)
} else {
    &message_queue         // drained by try_receive()
};

Chunked reassembly, because job documents exceed the buffer

A payload larger than the 4 KB inbound buffer is delivered as Details::InitialChunk (carries the topic and total_data_size) followed by N × Details::SubsequentChunk (topic: None). The thread accumulates into partial: Option<(String, Vec<u8>, usize)> and only enqueues once complete. This exists specifically because an IoT job document carrying a presigned S3 URL does not fit in one frame. Only one message can be in flight — a new InitialChunk discards an incomplete predecessor with a warning.

Worth knowing

Publishes are QoS 1, subscriptions are QoS 0, keep-alive is 60 s. publish() returns Err immediately when disconnected — it does not buffer, despite the log line reading “will queue messages temporarily”. Nothing retries a dropped telemetry publish.

05 OTA over AWS IoT Jobs

The headline change of this branch. The entire HTTP-metadata-polling design — a Basic-auth JSON endpoint on firmware.jantaus.com — has been removed.

master — pull from a web host

  • GET firmware.jantaus.com/firmware/test2/metadata{id}.json with Authorization: Basic
  • Credentials device1A / device1A hardcoded in the switchboard
  • Same Basic auth reused for the firmware download
  • NVS carried version, prev_version, first_boot
  • Success reported by publishing logs/firmware_update on the next boot
  • Polled every 2 hours during the nighttime sleep loop

repositioning — AWS IoT Jobs

  • Job requested over MQTT on the device's own reserved topic
  • No credentials in the firmware at all — mTLS is the auth
  • Download URL is presigned S3; no auth header is sent
  • NVS carries first_boot and pending_job_id
  • Success reported to the Jobs API only after boot validation passes
  • Checked once per boot — see finding 01

The handshake

Job document schema

This is a custom document, not the standard AWS OTA shape. The cloud-side job template must emit all four fields or the device rejects it:

{
  "version":      "1.1.5",          // semver, strict > comparison
  "size":         1399984,          // bytes, must be non-zero
  "download_url": "https://…s3…", // presigned; long, hence buffer_size_tx 4096
  "sha256":       "sha256:<64 hex>"  // prefix optional, length + hex validated
}
The one that bit them

No Authorization header is sent on the download. A presigned S3 URL already carries its SigV4 signature in the query string, and adding a second mechanism makes S3 reject the request with 400 — Only one auth mechanism allowed. The code comments call this out explicitly so nobody reinstates the old Basic-auth header.

There is no signature field. The build is checksum-only — it detects corruption, not tampering — and the source says so in a comment as a deliberate small-fleet trade-off. Adding signature verification is a single insertion point in run_version_compare.

06 Boot sequence

The Network FSM ticks every 10 ms, so these transitions happen back to back. This is a genuine ordering — each step depends on the one before it.

#StateWhat it does, and what can go wrong
1WifiInitialize If RESET_NVS_CREDENTIALS is true, force wifi_ssid / wifi_pass / tz_posix back to the .env values. Otherwise seed only the keys that are missing, so flash-time provisioning survives. Then bring up the Wi-Fi driver.
2InitNetworkServices Set the POSIX TZ and call tzset, read the DS3231; if the year is outside 2024–2100 fall back to SNTP with a 60 s budget and write the corrected UTC back to the RTC. Then construct the MQTT client. On failure it holds and retries indefinitely rather than panicking.
3BootValidation Version now comes from env!("CARGO_PKG_VERSION"), not the old NVS version key. Publishes logs/boot with the hardware reset reason. If first_boot == 1: factory slot skips marking; a passing diagnostic calls mark_running_slot_valid() and confirms the pending job; a failing one calls mark_running_slot_invalid_and_reboot() — a rollback. Subscribes to the command topic.
4Ota Raises ota_active on the bulletin, publishes a heartbeat, sleeps 3 s, runs the Jobs handshake, lowers the flag. Reached from exactly one place, exactly once.
5WifiConnectIfDisconnected Steady state for the life of the device. Reconnects Wi-Fi (30 s wait, errors swallowed so a flaky AP cannot kill the thread), drains one internal FSM command per tick, and branches to the heartbeat every 15 minutes.

sdkconfig.defaults

Three entries carry the OTA behaviour, two of them added on this branch:

  • CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y — a freshly flashed image boots PENDING_VERIFY and the bootloader reverts it unless the firmware explicitly validates itself. This is what makes step 3 of the boot sequence load-bearing.
  • CONFIG_APP_PROJECT_VER_FROM_CONFIG=y with a pinned "1.1.4" — the comment explains why: git describe output can exceed 24 characters and overflow the heapless::String<24> inside EspOta::get_running_slot(), panicking boot validation.
  • CONFIG_ESPTOOLPY_FLASHSIZE_8MB=y plus --flash-size 8mb on the espflash runner — without both, the partition table does not fit.

Also relevant: the task watchdog is configured with a 1800 s timeout and PANIC=y, and the file still carries a TODO: CHANGE WDT_TIMEOUT.

08 Freezing the motor while OTA runs

Commit d86d759. A 2 MB download over Wi-Fi while a stepper is mid-travel is not a combination anyone wants in the field.

The Network FSM raises ota_active on the shared bulletin before the Jobs handshake and lowers it on every exit path. Six Motion states read it as their first statement and return Hold:

MotionInit · MotionBeginHoming · MotionMoving · MotionTracking · MotionMaintenance · MotionErrorLoop

Because the Motion FSM ticks at 100 ms, the tower parks within about a tick of the next state boundary. The gating is cooperative and entry-only: Motion::move_by() blocks until the stepper reaches its target or aborts on stall, overshoot or power loss, so a move already in flight runs to completion rather than being abandoned with the relay energised. That is the right trade-off.

The mechanism has one sharp edge, documented as finding 02 below.

09 Findings

Ordered by what I would act on first. Severity encodes blast radius on a deployed tower, not effort to fix.

Critical · 01

The 2-hour periodic OTA check was lost in the FSM refactor

On master, the nighttime sleep loop inside motion/src/lib.rs polled for an update every two hours while waiting for sunrise. On this branch that loop is gone, and its intended replacement never wired up:

MotionEvent::CheckForOTA is defined but never constructed anywhere — tracking.rs only matches on it. And FSMCommand::PerformOTA is never handled — the steady-state match arm drops it in _ => {}. The Ota state is reachable only from BootValidation, which runs once.

Net effect: a deployed tower requests a job exactly once, at boot, and never again. Queue a job against a running tower and nothing happens until it reboots for an unrelated reason. Since fleet rollout is the entire point of the Jobs migration, this probably wants fixing before the branch ships.

High · 02

Pausing for OTA loses MotionMoving's return state

Fsm::step() calls self.previous_state.take() before invoking process, and on Hold it is not restored — the trait docs state this explicitly. MotionMoving resumes its caller through that previous_state, so when it hits the ota_active guard and returns Hold, the Option is dropped on the floor.

The next tick after OTA clears logs “No previous state found after motion movement; re-initializing” and falls back to MotionInit. If the OTA window overlaps a homing sweep — likely, since homing starts while the Network FSM is still doing Wi-Fi, SNTP and MQTT — the tower restarts motion init mid-sweep instead of resuming.

MotionMaintenance is immune because it stores return_to in self. Same fix applies here.

High · 03

Remote commands drain at most once every 15 minutes

transport::process_one() is called from exactly one place: WifiPublishHeartbeat, which only runs when last_heartbeat_instant.elapsed() > 15 min. It handles one message per visit.

So a get_status can sit unanswered for a quarter of an hour, and N queued commands take N × 15 min to drain, while the inbound VecDeque grows without bound. WifiConnectIfDisconnected already runs every 10 ms and is the natural place to drain it.

Medium · 04

pending_job_id is read into a 64-byte buffer

AWS IoT job IDs may be up to 64 characters, and EspNvs::get_str needs room for the trailing NUL. A maximum-length job ID fails to read back, so a perfectly good OTA never gets confirmed SUCCEEDED and the job sits IN_PROGRESS until it times out. Eighty bytes is free insurance.

Medium · 05

Transient network trouble triggers a firmware rollback

boot_diagnostic() returns false if Wi-Fi is down or three MQTT publish attempts fail, roughly 36 s of trying. On an OTA boot that calls mark_running_slot_invalid_and_reboot() — so a good new image gets reverted because the access point was flaky for a minute. Worth deciding deliberately whether reachability should be the rollback criterion, or whether it should be paired with something local.

Medium · 06

Version metadata disagrees with itself

Cargo.toml, CONFIG_APP_PROJECT_VER and switchboard.default_version all say 1.1.4. But CHANGELOG.md lists 1.1.5 as released and the tracking loop logs “Tracking loop duration (v1.1.5)”. Commit 862ccb2 reverted 1.1.5 back to 1.1.4 under the message “version fix”, presumably to make an OTA to 1.1.5 testable. Because the comparison is a strict >, a device can never be told to re-flash its own version or to downgrade — worth knowing before someone tries to push a hotfix that way.

Low · 07

The top-level README describes the old certificate layout

It says to drop certificates into crates/infrastructure/network and names them [DEVICE_ID]-certificate.pem.crt. Both are wrong now: they belong in certs/ as tower_{DEVICE_ID}-certificate.pem.crt. certs/README.md is correct; the top-level one will send a new teammate into a build error they cannot explain.

Smaller things, noted not urged

  • No SUBACK wait before publishing the $next/get request — a 500 ms sleep stands in, self-documented as a stopgap and the first thing to harden if job responses start going missing.
  • The request sends {} with no clientToken, so responses cannot be correlated. Safe only because there is exactly one requester and the $aws/ queue is dedicated.
  • crates/motion still declares ota.workspace = true but no longer uses it.
  • src/logic/watchdog.rs is a complete, well-documented ESP-IDF task-watchdog wrapper marked #![allow(dead_code)] — no FSM instantiates or feeds it. The infrastructure exists; nothing uses it.
  • Telemetry publishes are fire-and-forget. A publish that fails while Wi-Fi is down is logged and dropped, never retried.
  • No CI workflows exist on any branch, despite the changelog claiming GitHub Actions were added. The hooks/pre-commit script (fmt, build, clippy) is the only automated gate, and it has to be installed manually.
